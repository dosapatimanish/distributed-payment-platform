# Bank-style Identifier Scheme

Replaces the platform's `UUID.randomUUID().toString()` identifiers (`userId`, `walletId`,
`transactionId`) with structured, mostly-numeric identifiers in the style of a core-banking
system, and adds a `currency` reference table and a `unit_master` (bank business-date) record.

**Status: implemented and verified** (all 5 services, full stack). Decisions below are final;
there is no backward compatibility — every earlier Postman literal / curl example / UUID-based
test fixture changed with it.

**Verified end to end** (`docker compose up -d --build`, fresh volume): wallets created as
`011000000001` (USD) / `031000000001` (INR) for CIF `1000000042`; `POST /conversions` minted
`0120260827000001` then `0120260827000002` (daily sequence in `txn_sequence`, date from
`unit_master`); saga `COMPLETED`; ledger legs for the dest account and for `SC0000000000` (the
SC-prefixed clearing account, currencies net to zero); `saga_step_log.account_no` populated for
`DEBIT` / `CREDIT` / `DEBIT_FOR_PAYMENT`; idempotent replay returned the identical response;
`ddl-auto=validate` passed for every service against the new columns.

## Final decisions

| Item | Decision |
|---|---|
| 2-digit currency code | Custom, in `currency.short_code`: `USD=01`, `EUR=02`, `INR=03`, `GBP=04`. |
| Storage | `VARCHAR2` strings (leading zeros, no arithmetic). |
| `currency` table | Owned by **wallet-service**, `GET /api/v1/currencies` + `/{code}`. conversion-orchestrator caches the `code → short_code` map at startup. |
| CIF | **Client-supplied.** Validated only: exactly 10 characters, digits only (`^\d{10}$`). No minting endpoint. |
| Account number | `[currency short_code 2][CIF prefix 5][sequence 5]` = **12 chars**, `VARCHAR2(12)`. Sequence is per `(short_code, CIF prefix)`. `UNIQUE(account_no)` as a hard backstop. |
| FX clearing account | Special value `SC0000000000` (`SC` + 10 digits) — same 12-char column, never a customer account. Replaces `SYSTEM-FX-CLEARING`. |
| Transaction ID | `[source-currency short_code 2][business date YYYYMMDD 8][daily sequence 6]` = **16 chars**, `VARCHAR2(16)`. `ledger_entry.transaction_id` stays `VARCHAR2(64)` for the `-reversal` suffix. |
| Business date | `unit_master` single-row table, `business_date` column. A Spring `@Scheduled` job in conversion-orchestrator rolls it forward by one day on a cron. The transaction ID's date and daily sequence both key off this value, not wall-clock. |
| Daily transaction sequence | Counter row `txn_sequence(business_date PK, next_val)` in conversion-orchestrator. A new business date creates a fresh row starting at 1; incremented under `SELECT … FOR UPDATE`. |
| Schema migration | Rewrite each service's `V1__init.sql` (no data to preserve — same approach as the Oracle migration). Needs `docker compose down -v` before the next `up`. |

## Identifiers in detail

### CIF (replaces `userId`)

10-digit customer number, **supplied by the client** on `POST /api/v1/wallets` (and echoed
through the conversion request). The only server-side rule: `@Pattern(regexp = "\\d{10}")` —
reject anything that isn't exactly ten digits. Example `1000000042`.

### Account number (replaces `walletId`)

`short_code (2) + CIF prefix (first 5 of the CIF) + sequence (5)` → 12 chars.

```
 01      10000    00001      ->  011000000001
 ^cur    ^CIF[0:5] ^ nth account for (cur, CIF-prefix)
```

- Sequence source: `account_sequence(currency_code, cif_prefix, next_val)`,
  `PRIMARY KEY (currency_code, cif_prefix)`, `MERGE` + `RETURNING` (or `SELECT … FOR UPDATE`
  then `UPDATE`) to hand out the next value. Padded to 5 with `LPAD(…, 5, '0')`.
- 99 999 accounts per currency per CIF-prefix group. Two CIFs sharing the same first five
  digits share that pool; `UNIQUE(account_no)` on `wallet` makes any real collision fail loudly
  rather than corrupt balances.
- Generated in `WalletService.createWallet` — it has the CIF and currency from the request and
  the `currency` table locally, no cross-service call.
- FX clearing account is `SC0000000000`, inserted/used as-is; it is never generated by this
  path and never has a `wallet` row (ledger-only).

### Transaction ID (replaces `transactionId`)

`source-currency short_code (2) + business_date (YYYYMMDD) + daily_sequence (6)` → 16 chars.

```
 03      20260827   000517   ->  0320260827000517
 ^srcCcy ^unit BD    ^ 517th txn on that business date
```

- Minted in `ConversionService.startConversion`, before the `conversion_transaction` row is
  written (it is that row's PK).
- Needs the source currency's `short_code` — from the orchestrator's startup-cached
  `code → short_code` map (loaded via `CurrencyServiceClient.getAll()` calling wallet-service
  `GET /api/v1/currencies`).
- Needs the business date and the next daily sequence — from `BusinessDateService` /
  `txn_sequence` (both local to conversion-orchestrator).
- Daily sequence caps at 999 999 transactions per business date. Fine for the demo.
- Direct `POST /api/v1/wallets/{accountNo}/debit` outside a saga still takes a `transactionId`
  in its body; the caller supplies it and wallet-service validates `^\d{16}$` (it does not mint
  one).

## `currency` table (wallet-service)

```sql
CREATE TABLE currency (
    code         VARCHAR2(3)  NOT NULL,   -- ISO 4217 alpha
    numeric_code VARCHAR2(3)  NOT NULL,   -- ISO 4217 numeric
    short_code   VARCHAR2(2)  NOT NULL,   -- custom 2-digit code used in account / txn ids
    name         VARCHAR2(64) NOT NULL,
    minor_units  NUMBER(1)    NOT NULL,
    active       VARCHAR2(1)  DEFAULT 'Y' NOT NULL,
    CONSTRAINT currency_pkey PRIMARY KEY (code),
    CONSTRAINT uk_currency_short_code   UNIQUE (short_code),
    CONSTRAINT uk_currency_numeric_code UNIQUE (numeric_code),
    CONSTRAINT currency_active_check CHECK (active IN ('Y','N'))
);
INSERT INTO currency VALUES ('USD','840','01','US Dollar',      2,'Y');
INSERT INTO currency VALUES ('EUR','978','02','Euro',           2,'Y');
INSERT INTO currency VALUES ('INR','356','03','Indian Rupee',   2,'Y');
INSERT INTO currency VALUES ('GBP','826','04','Pound Sterling', 2,'Y');
```

`GET /api/v1/currencies` → active rows. `GET /api/v1/currencies/{code}` → one or
`404 CURRENCY_NOT_FOUND`. Read-only, no `Idempotency-Key`. `WalletService.createWallet` rejects
a request whose `currency` has no active row (`UnsupportedCurrencyException`).

## `unit_master` + business-date roll (conversion-orchestrator)

```sql
CREATE TABLE unit_master (
    unit_id       VARCHAR2(8)  NOT NULL,
    unit_name     VARCHAR2(64) NOT NULL,
    business_date DATE         NOT NULL,
    CONSTRAINT unit_master_pkey PRIMARY KEY (unit_id)
);
INSERT INTO unit_master (unit_id, unit_name, business_date)
VALUES ('MAIN', 'Main Unit', TRUNC(SYSDATE));

CREATE TABLE txn_sequence (
    business_date DATE   NOT NULL,
    next_val      NUMBER(9) DEFAULT 1 NOT NULL,
    CONSTRAINT txn_sequence_pkey PRIMARY KEY (business_date)
);
```

- `BusinessDateService.current()` reads `unit_master` (`unit_id = 'MAIN'`).
- `BusinessDateRollJob` — `@Scheduled(cron = "${unit.business-date.roll-cron:0 0 0 * * *}")` —
  `UPDATE unit_master SET business_date = business_date + 1 WHERE unit_id = 'MAIN'`. Cron is a
  property so a demo can roll it faster.
- `TransactionSequenceService.next(businessDate)` — `MERGE` a `txn_sequence` row for that date
  (insert `next_val = 1`, else `next_val = next_val + 1`) under row lock, returns the value.
- `TransactionIdGenerator.next(sourceCurrencyCode)` = `shortCode + businessDate(yyyyMMdd) +
  lpad(nextSeq, 6)`.

## `saga_step_log` — new column

Add `account_no VARCHAR2(12)` (nullable — steps like `RATE_LOCK` / `CONSUME_LOCK` touch no
account). `ConversionService.logStep(txn, step, status, payload, accountNo)` records which
account a step acted on (source for `DEBIT` / `COMPENSATE_DEBIT`, destination for `CREDIT` /
`DEBIT_FOR_PAYMENT` / `COMPENSATE_CREDIT`, `null` otherwise).

## Secondary ids — sequence-based, not UUID

The remaining app-assigned keys are identifiable running numbers instead of random UUIDs.

**Child tables — composite PK `(transaction_id, seq_no)`.** The transaction id is a sibling
column, so the sequence number itself is just `01`, `02`, `03` … and its place in the sequence
is obvious:

| Table | Composite PK | `seq_no` meaning |
|---|---|---|
| `saga_step_log` | `(transaction_id, step_no)` | step order within the saga (`01` = rate lock, `02` = debit, …) |
| `ledger_entry` | `(transaction_id, entry_no)` | leg order within the posting (`01`..`04`); a reversal posts under `transaction_id = {txn}-reversal` |

`step_no` = `countByTransactionId + 1`; `entry_no` = the leg's list index. Both `VARCHAR2(4)`,
`%02d`-formatted (`@IdClass` composite key on the entity).

**Standalone tables — `PREFIX + 10-digit Oracle sequence`.** No natural parent to scope to, so a
global running number with a type prefix:

| Table | Id | Sequence | Example |
|---|---|---|---|
| `fx_rate_lock` | `lock_id` | `fx_rate_lock_seq` | `LK0000000001` |
| `fx_rate` | `rate_id` | `fx_rate_seq` (feed insertion order) | `FR0000000001` |
| `merchant_payment` | `payment_id` | `merchant_payment_seq` | `PM0000000001` |
| `wallet_reservation` | `reservation_id` | `wallet_reservation_seq` | `RS0000000001` |

From a per-service `SequenceIds` helper (`SELECT seq.NEXTVAL FROM dual`, `PREFIX + %010d`).

**Verified live:** `saga_step_log` rows `(0120260827000001, 01)`…`(…, 07)`; `ledger_entry` rows
`(0120260827000001, 01..04)` incl. the `SC0000000000` clearing legs; `LK0000000001` in
`fx_rate_lock`; `FR000000000n` in `fx_rate`.

## Known limitations (accepted for the demo)

- Account number uniqueness relies on `UNIQUE(account_no)`; two CIFs sharing a 5-digit prefix
  compete for the same 99 999-account pool per currency.
- `business_date` only advances on the cron — a long-running stack with no roll drifts behind
  wall-clock (this is how a real EOD works, but there's no fast-forward-on-startup).
- Daily transaction sequence caps at 999 999 per business date.
- CIF is trusted from the client (format-checked only) — no customer master, no "does this CIF
  exist" check.
